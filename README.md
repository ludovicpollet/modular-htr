# Modular HTR

This work in progress puts together a few of the research scripts and experimental implementations I made over the last years into a simple but usable recognition "engine". It aims to bridge together the advances published in a few papers (see below for the [references](#references)) whose techniques looked especially interesting for my low ressource approach in a convenient CLI that I can use for my own historical research.

## Features

- Modular CNN + sequence encoder architecture, with named presets reproducing configurations from recent papers and full per-parameter control for experimentation.
- CNN backbones: configurable residual networks (with optional bottleneck blocks, squeeze-excitation, flexible downsampling) and adapted ConvNeXt variants with optional ImageNet-pretrained weights.
- Sequence encoders: bidirectional LSTM or Transformer with relative sinusoidal positional bias.
- CTC training with greedy and beam-search decoding, optional n-gram language model integration (KenLM), and an auxiliary shortcut CTC head for improved gradient flow.
- Transfer learning pipeline: checkpoint loading with automatic alphabet merging, configurable head reinitialization, and progressive stage unfreezing.
- Data pipeline: PageXML compilation, HuggingFace Hub integration, multi-dataset training, width-bucketed batching, and GPU-accelerated augmentation (kornia).
- Dataclass-driven configuration with a CLI generated by tyro: every parameter is discoverable and overridable from the command line.

## Ideas and goals

Here are the basic starting points :
- Medieval handwriting is still a challenge for most recognition systems, unless very large training datasets are used. The production of annotated data is extremely costly.
- Latest research on line-based HTR (and its application to the medieval domain) is focusing on very large models like TrOCR. The effectiveness of those models is, among other things, contingent on massive pretraining corpora and compute budgets that are impractical for low-resource medieval domains where labelled data is scarce and script variety is high.
- Lighter convolutional models can also take advantage of modern training techniques and pretraining to be competitive, especially in low-resources scenarios.

While still a work in progress, this project draws on several key findings from HTR research:

- [Retsinas et al. (2022)](#references) showed that a simple resnet + lstm + ctc architecture with a careful implementation is already a very good starting point that can be further enhanced by other techniques. I implemented a scheduled variant of the shortcut CTC head, a somewhat similar residual backbone, and options to use the max pool height collapse (with inverted images) recommended in the paper. The main difference is that I used variable width batches.
- [Diaz et al. (2021)](#references) makes a compelling argument for the value of CTC based decoders when coupled with simple language models, while demonstrating that a self-attention encoder can replace the lstm while being parameter-efficient, without the need for a full transformer encoder-decoder architecture. I implemented a self-attention encoder with n-gram assisted CTC decoding, but with a much simpler n-gram building technique. They use also a different backbone, and I'm not sure exactly now much my implementation differs since the paper doesn't provide all the details. 
- [The ConvNeXt (Liu et al.)](#references) paper has also shown that a convolutional feature encoder, when using modern advances and training techniques can scale successfuly and outperform both the ViT and SWIN transformer on classification tasks, especially when one is concerned about efficiency. I'm using two variants, adapted to be suitable for HTR with CTC constraints.

The goal is to experiment with mixing those techniques in a real HTR scenario with scarce medieval data in the final domain. Also, I just wanted to learn how to do it.

>Please understand that the named default configurations (e.g. "Pylaia", "Retsinas") are not intended to be exact replications of the implementations or papers they refer to, because I allowed myself a few tweaks and generalisations to keep things simple (for example, I decided to use "norm-first" residual blocks and GELU activation in all such blocks for all configurations).

## Evaluation
To get an idea of the perfmorance, this is an early evaluation of the residual backbone with the self-attention positional encoder and CTC with n-gram lm decoder on a few well known benchmarks. The model has been pretrained on a ~500k lines generic dataset to make comparisons with large scale pretrained transformer models a bit more fair.

|Dataset |val CER %| val WER %| test CER %| test WER %| 
|-------:|:-------:|:--------:|:---------:|:---------:|
|[IAM (line)](https://huggingface.co/datasets/Teklia/IAM-line)   |1.75|7.61 |2.63|10.02| 
|[TRIDIS](https://huggingface.co/datasets/magistermilitum/Tridis)|5.42|18.36|6.37|22.81| 
|[CATMuS modern](https://huggingface.co/datasets/CATMuS/modern)  |3.52|12.04|7.52|23.29|

Note that errors on the tridis dataset are mostly commas: in most cases, the model is probably right that they do not exist (ground truth punctuation is modernised). 

## Usage

### Installation
Use [uv](https://github.com/astral-sh/uv) :
```bash
git clone https://github.com/ludovicpollet/modular-htr.git && cd modular-htr
uv sync
uv run modular-htr --help
```

### Dependencies

The project deliberately relies on a small set of well-maintained libraries to stay compatible with recent PyTorch releases and keep the overall surface area manageable:

- **PyTorch ecosystem**: `torch`, `torchvision`, `torchaudio`, `kornia` (GPU augmentation).
- **Data**: HuggingFace `datasets`, `Pillow`, `lxml` (PageXML parsing).
- **Decoding**: `flashlight-text` and `kenlm` for beam search with language model support.
- **CLI and utilities**: `tyro` (CLI generation from dataclasses), `torchinfo`, `tabulate`, `tqdm`.
- **Optional**: `timm` (only needed for loading pretrained ConvNeXt weights) — install with `uv sync --extra pretrained`.

No high-level training framework (Lightning, MMDetection, etc.) is used; training loops, checkpointing, and metrics are implemented directly.

### Configuration and CLI usage
I used a structured `dataclasses.dataclass` configuration file and the [tyro](https://github.com/brentyi/tyro) library to build the CLI. You can rely on the help messages to consult the available options for each subcommand, for example :

```bash
# show the main subcommands (i. e. train, finetune, etc):
uv run modular-htr --help

# show the training options:
uv run modular-htr train --help

# after the main one, the nested subcommands use the ":" syntax, for example (note that the help message will only show the options related to the last subcommand, in this case the scheduler options):
uv run modular-htr train model:pylaia-paper scheduler:onecycle --help

# options are nested with the dot syntax, and need to be placed after their related subcommand:
uv run modular-htr train optim.lr 3e-4 scheduler:cosine --scheduler.eta-min 3e-5

# helpful comments are displayed for all parameters that are not defined inside a default named config like model:retsinas; those are only displayed when using the fully modular model and backbone configurations such as
uv run modular-htr model:modular --help
uv run modular-htr model:modular model.backbone:modular --help
```

### Choosing a pre-configured model architecture
At the moment, the model that performs best for most of **my** use cases uses a residual backbone such as the one proposed by [Retsinas et al.](#references), combined with a multi-head self-attention (with relative sinusoidal positional bias) sequence encoder, and CTC decoding with an optional simple n-gram language model like suggested by [Diaz et al.](#references)

Swapping the resnet-like backbone with an adapted ConvNeXt variant yields promising results, and if compute resources are large enough, the nearly original ConvNeXt-tiny backbone (with adapted downsampling layers) can also be used. This last variant will load Imagenet pretrained weights instead of the standard initialization.

For smaller datasets without a complex pretraining strategy, I would advise using the default Retsinas configuration with the CTC shortcut and the LSTM sequence encoder.
```bash
uv run modular-htr train model:retsinas-mha

# the same but using bottleneck blocks instead of standard residual blocks for the large ones to save compute
uv run modular-htr train model:retsinas-mha model.backbone.bottleneck-after 256

# The original Pylaia architecture from Puigcerver's paper :
uv run modular-htr train model:pylaia-paper

# The smaller default variant in the current implementation maintained by Teklia :
uv run modular-htr train model:pylaia-modern

# The backbone can be swapped and/or specific parameters overriden:
uv run modular-htr train model:retsinas model.backbone:convnext --model.num-layers 2
```

### Compiling a dataset from PageXML

Converts PageXML annotation files and the corresponding page images into a HuggingFace `DatasetDict` with train/test splits (90/10). The resulting dataset can then be used for training with the `data.dataset:local` subcommand.

```bash
uv run modular-htr compile-dataset --xml path/to/xml --img path/to/images --out path/to/output
```

### Training

```bash
# Training from a local dataset:
uv run modular-htr train --run-name my-run model:retsinas \
    data.dataset:local --data.dataset.path path/to/hfds

# Training from a HuggingFace Hub dataset:
uv run modular-htr train --run-name my-run model:retsinas \
    data.dataset:hub --data.dataset.name Teklia/IAM-line
```

Training artifacts (checkpoints, metrics CSV, config dump, model summary) are saved under `runs/<timestamp>_<run-name>/`.

### Finetuning from a checkpoint

Loads a pretrained checkpoint, automatically merges the alphabets (handling new and dropped characters), and rebuilds the output head. Supports stage freezing with progressive unfreezing and configurable head reinitialization.

```bash
uv run modular-htr finetune --run-name my-finetune \
    --from-checkpoint runs/.../checkpoint_best.pt \
    data.dataset:hub --data.dataset.name Teklia/IAM-line
```

The finetuning strategy can be configured:
```bash
# freeze the first 2 CNN stages and unfreeze them after 5 epochs:
uv run modular-htr finetune --run-name my-finetune \
    --from-checkpoint runs/.../checkpoint_best.pt \
    --strategy.freeze-n-stages 2 --strategy.unfreeze-epoch 5 \
    data.dataset:hub --data.dataset.name Teklia/IAM-line
```

### Evaluation

Evaluate a checkpoint on any explicit split from a local or Hub dataset.

```bash
# Evaluate on a local dataset test split:
uv run modular-htr evaluate --checkpoint runs/.../best_010_cer_0.1234.pt \
    data.dataset:local --data.dataset.path path/to/hfds

# Evaluate on a specific split from HF Hub:
uv run modular-htr evaluate --checkpoint runs/.../best_010_cer_0.1234.pt \
    --split validation \
    data.dataset:hub --data.dataset.name Teklia/IAM-line

# Evaluate with beam decoding + LM and save full JSON report:
uv run modular-htr evaluate --checkpoint runs/.../best_010_cer_0.1234.pt \
    --decoder.mode beam --decoder.lm-path lm/my_model.bin \
    --output-json runs/eval/report.json \
    data.dataset:hub --data.dataset.name Teklia/IAM-line
```

### Dataset analysis

Computes width distributions, CTC feasibility ratios for various stride values, and helps choose `fixed_height` and backbone downsampling parameters. This is useful for making informed architecture decisions before training, especially when working with a new dataset.

```bash
uv run modular-htr analyse-dataset dataset:hub --dataset.name Teklia/IAM-line
```

### Multi-dataset training

Multiple HuggingFace Hub datasets can be combined for training using a JSON configuration file. Each source can specify its own column names and split configuration. After loading, all sources are normalized to canonical column names.

```bash
uv run modular-htr train --run-name pretrain model:retsinas \
    data.dataset:multi --data.dataset.sources-file configs/pretrain.json
```

The JSON file is an array of source objects:
```json
[
    {"name": "CATMuS/medieval", "img_col": "im"},
    {"name": "Teklia/IAM-line"},
    {"name": "Teklia/RIMES-2011-line"}
]
```

Each object requires a `name` field (HuggingFace Hub dataset name). Optional fields: `img_col`, `text_col`, `train_split`, `val_split`.

### N-gram language model (KenLM)

A character-level n-gram language model can be used during beam-search decoding to bias predictions toward plausible character sequences. This is especially helpful in low-resource scenarios and can noticeably reduce CER without any additional training.

#### Installing KenLM build tools

The Python `kenlm` package (installed with the project dependencies) handles model querying, but **building** a model requires the KenLM command-line tools (`lmplz`, `build_binary`, and optionally `interpolate`). These must be compiled from source.

#### Building a language model

The `build-lm` subcommand builds a binary KenLM model from training text. Text can come from a HuggingFace dataset or from plain text files (one line per sample). Internally, each line is converted to a character-level format where characters are space-separated and the actual space character is replaced by a placeholder.

```bash
# From a HuggingFace dataset (uses the train split by default):
uv run modular-htr build-lm --output lm/my_model.bin --order 6 \
    source:dataset --source.dataset.name Teklia/IAM-line

# From plain text files:
uv run modular-htr build-lm --output lm/my_model.bin --order 6 \
    source:text --source.paths file1.txt file2.txt

# Unicode normalization is applied before building (default: NFKC):
uv run modular-htr build-lm --output lm/my_model.bin --unicode-normalize NFC \
    source:dataset --source.dataset.name Teklia/IAM-line
```

To prepare models for later interpolation, add `--intermediate`:
```bash
uv run modular-htr build-lm --output lm/domain_a.bin --intermediate \
    source:text --source.paths domain_a.txt

uv run modular-htr build-lm --output lm/domain_b.bin --intermediate \
    source:text --source.paths domain_b.txt

# Interpolate the two models:
uv run modular-htr interpolate-lm \
    --model-dirs lm/domain_a_intermediate lm/domain_b_intermediate \
    --weights 0.7 0.3 \
    --output lm/interpolated.bin
```

#### Using a language model for decoding

Pass the LM path and decoding parameters when training or finetuning. The decoder is used during validation to compute CER/WER:

```bash
uv run modular-htr train --run-name my-run model:retsinas \
    --decoder.mode beam --decoder.lm-path lm/my_model.bin \
    --decoder.lm-alpha 0.5 --decoder.word-score 0.0 \
    data.dataset:hub --data.dataset.name Teklia/IAM-line
```
These parameters should be tuned on the validation set.
